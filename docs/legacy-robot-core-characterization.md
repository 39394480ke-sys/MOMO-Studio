# Legacy robot core characterization

## Evidence boundary

- Legacy repository: `https://github.com/39394480ke-sys/MOMO_RobotARM.git`
- Audited commit: `ff8bbda0c2222cb57951c7913f7f12f5777b98fa`
- Commit subject: `feat: add multi-arm control and dual vision workflows`
- Inspection was static and read only. Legacy files were inspected only with `git show` and `git ls-tree` at the audited commit.
- No Legacy module was imported or executed. No serial port, servo bus, calibration operation, motion command, camera, or other hardware path was used.
- No `current.local.json`, local serial configuration, runtime state, untracked file, or tracked calibration-backup content was opened. A backup path is visible in the Git tree, but its contents are intentionally outside this characterization.
- No Legacy implementation or asset is copied by Stage 2. The new modules independently express selected contracts behind the MOMO Studio domain, application, port, adapter, and API boundaries.

This document characterizes what the pinned Legacy source does. It does not certify that the source's hardware constants, profiles, calibration values, or safety behavior are correct for a physical MOMO robot.

## Authority labels

| Label | Meaning |
|---|---|
| `PRODUCT` | The MOMO Studio product contract is authoritative: V1 enables J11-J15, V2 enables J10-J15, V2 J10 is prismatic in mm, Stage 2 is Dry Run only, and hardware access is disabled. |
| `LEGACY_OBSERVATION` | The statement is authoritative only as a description of source behavior at the pinned Legacy commit. |
| `CHARACTERIZATION_ONLY` | A formula, constant, scale, bound, mode, or data shape is useful for tests or provenance, but is not approved for real hardware. |
| `RETIRED` | The behavior is deliberately not a MOMO Studio contract. Reintroducing it requires a later scoped decision. |

When a Legacy observation conflicts with `PRODUCT`, the product contract wins. In particular, fixed six-joint constants, a V1 rail, `target_deg` naming for J10, and the Legacy V1 profile are not authoritative.

## Preserved safety invariants

Stage 2 preserves or strengthens these independently implemented invariants:

1. Unknown joints fail closed.
2. Mapping inputs and logical positions must be finite and unit-explicit.
3. A mapping scale cannot be zero, and raw-count scale must be positive.
4. Direction must be `-1` or `1`.
5. Profile and calibration raw ranges must be valid and must overlap.
6. Effective logical limits are the intersection of declared logical limits and raw-reachable limits.
7. Calibration variant, profile fingerprint, enabled-joint set, completeness, and template status are reported separately.
8. Missing or template calibration does not prevent Dry Run, but it never authorizes real hardware.
9. Robot lifecycle commands are serialized, variant selection is disconnected-only, and Stop is available and idempotent in Dry Run.
10. Runtime state contains no serial port, real calibration, secret, or raw-servo command surface.

## Deliberately changed behavior

- V1 never inherits J10. The Legacy root profile, loader default, globals, and fleet fallback lose authority.
- J10 is not described as degrees. Unit-neutral mapping names are used, and units come from the profile.
- Dry Run connect does not create a real-capable controller and does not import a Feetech or serial library.
- Dry Run has no simulated motion, register writes, torque state, gripper control, Home, jog, pose application, or motion playback.
- Calibration examples are immutable templates matched to a profile fingerprint. Stage 2 never creates or updates real calibration.
- Runtime mode cannot be switched to real. Attempts to enable real motion or non-disabled hardware access fail configuration validation.
- The API has lifecycle and diagnostic routes only. It has no raw driver, movement, Home, jog, pose, action, trajectory, camera, or fleet route.

## Later-stage gates

This characterization does not approve real motion. Before a future real adapter can use any Legacy-derived behavior, that stage must:

1. pin the source revision and retain this provenance trail;
2. use synthetic characterization tests before any hardware test;
3. verify all profile and calibration fields on the selected physical variant;
4. place every real command behind one reviewed safety entry point;
5. prove API and application code cannot reach a raw driver directly;
6. require explicit operator intent and provide tested cancellation and Stop behavior;
7. keep serial ports, device calibration, runtime state, captured data, and secrets local and untracked;
8. record physical verification evidence without converting example profiles into production profiles.
